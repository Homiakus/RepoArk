# RepoArk v0.8.0

v0.8 hardens RepoArk's distributed storage layer without changing the authoritative recovery unit: a verified immutable generation remains the object that is restored.

## Durable object lifecycle

The control plane now persists `object_refs`, unique `(digest, owner)` ownership, expiring `object_leases`, `erasure_sets`, and per-agent `erasure_shards`. A retry therefore cannot double-count the same logical shard owner, and CAS garbage collection must preserve any digest with a positive durable reference or active lease.

## Distributed erasure

Large immutable CAS objects can be encoded as Reed–Solomon `data_shards + parity_shards`. Each shard is itself a SHA-256 CAS object. When distributed mode is enabled, shard indices are assigned to eligible mTLS storage agents with failure-domain-aware deterministic placement and transferred with the same encrypted/resumable X25519 + AES-GCM relay used by the HA data plane.

Health is stricter than a simple copy count: RepoArk evaluates whether losing each represented failure domain would still leave at least `data_shards` unique shard indices. Generation replication remains the primary disaster-recovery contract; distributed erasure is an additional repair/durability layer.

## Scrub and repair

The scrubber selects a bounded deterministic sample per day, hashes objects against their CAS digest and optionally repairs them. Local repair reconstructs from Reed–Solomon parity into a temporary file and promotes it only after the original SHA-256 matches. Distributed repair is pinned to the agent that reported corruption and first assembles enough remote shards on that node.

## Disk health

Optional SMART/NVMe telemetry consumes JSON from `smartctl`/`nvme-cli` and computes an explainable risk score from overall SMART failure, NVMe critical warnings, media errors, endurance usage and temperature. This is a placement/evacuation signal, not a prediction guarantee.

## Tiering

Tiering is intentionally copy-only in v0.8. Verified CAS objects may be copied to a cold local root and/or an `rclone` destination, but the hot CAS object is not deleted by the tiering operation. Existing restore semantics therefore do not silently acquire a remote-storage dependency.
