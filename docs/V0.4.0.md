# RepoArk v0.4.0 — production data plane

v0.4 focuses on the difference between **having backups** and **operating a measurable recovery service**.

## Primary design changes

### 1. Content-addressed storage

Every eligible immutable payload can be hashed into `cas/sha256/<prefix>/<digest>`. The logical backup path remains a normal file. On filesystems that support hard links RepoArk swaps the logical file for a hard link to the CAS blob; otherwise it leaves the logical copy intact.

This keeps restore code simple and portable while deduplicating identical bundles/assets/packages across runs/accounts.

CAS GC never deletes based on inode link count. It hashes eligible files under all configured primary, fleet and GitLab logical roots, builds the reachable hash set, then removes unreferenced blobs. `--dry-run` is available for every production cleanup procedure.

### 2. Registry payload plane

GitHub Packages REST metadata is not the package binary transport for every ecosystem, so payload capture uses native registry protocols:

- npm registry HTTP metadata + tarball URL;
- NuGet V3 service index + flat-container package;
- Maven dependency resolution with an isolated local repository/settings file;
- RubyGems fetch with an isolated temporary HOME.

Payload failures remain platform warnings and do not change the recoverability result of the Git repository itself.

### 3. RPO/RTO policy

Policy evaluates:

- age of latest backup;
- failed repo/warning thresholds;
- manifest signature/KMS attestation;
- audit validity when required;
- age of repository restore drill;
- duration of repository restore drill;
- age of full GitLab drill;
- duration of full GitLab drill;
- age of off-site replication.

`/healthz` becomes a recovery-readiness endpoint when policy enforcement is enabled.

### 4. Independent trust anchors

Local Ed25519 remains the offline verifier. Optional AWS KMS creates a second detached attestation of `latest.json`. KMS does not replace the local key because disaster recovery must not require cloud control-plane availability merely to determine whether a backup is authentic.

### 5. Real GitLab integration test

The slow workflow is deliberately separate from fast CI. A real GitLab Omnibus container is resource-heavy, but it is the only meaningful validation that an application archive and exact image can actually complete a restore lifecycle.

## Compatibility

- manifest version: 4;
- config version: 4;
- v1-v3 configs continue to load with new fields supplied by defaults;
- existing backup trees remain readable;
- CAS is additive: restore does not require CAS path resolution.
