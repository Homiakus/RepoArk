# RepoArk v0.3.0 architecture increment

v0.3 promotes RepoArk from a single-account repository backup tool into a small recovery control plane.

## New subsystems

### Fleet orchestrator

`internal/fleet` derives isolated account configurations from the base configuration and runs account backups/verifications with bounded account-level concurrency. Repository-level concurrency remains controlled by `backup.concurrency`.

The two concurrency layers are intentionally separate so a large organization cannot starve smaller accounts.

### Actions artifact archival

`internal/githubapi` now implements the repository Actions artifact listing and archive download endpoints. `internal/backup` stores ZIP payloads below `actions-artifacts/`, writes per-file SHA-256 sidecars and records an index below repository metadata.

Expired artifacts are represented as degraded platform coverage rather than critical Git failure.

### Projects v2 capture

Projects v2 are account/organization objects, not repository Git objects. After repository discovery, RepoArk derives unique owners and performs a separate GraphQL export into `metadata/_account/projects-v2/`.

Project items are explicitly paginated instead of relying on one nested GraphQL window.

### Audit ledger

`internal/audit` uses a sequential SHA-256 hash chain. Every record commits to the previous record hash. With manifest signing enabled, RepoArk signs the ledger head with Ed25519 and stores a checkpoint + public key adjacent to the ledger.

### Immutable off-site path

`offsite.object_lock` uses AWS CLI as a narrow operational dependency instead of importing an AWS SDK into the core binary. Before sync, RepoArk checks both Object Lock configuration and bucket versioning. It never uses delete propagation for this destination.

### Namespace-preserving GitLab target

The GitLab API client now creates/locates a group for each GitHub owner and a project within that group. Legacy flattening remains configurable.

### Disposable full GitLab restore drill

A GitLab application backup is not considered fully validated merely because the tar file exists. The v0.3 drill launches a fresh container from the configured pinned image, restores configuration and application data, performs the documented Puma/Sidekiq stop sequence, runs the restore, restarts GitLab and executes `gitlab:check`.

The production container and production bind mounts are never used as restore targets.

## Compatibility

- v1/v2 configs are loaded on top of v3 safe defaults and promoted to `version: 3` in memory.
- v1/v2 manifests remain readable.
- `gitlab.preserve_namespaces: false` retains the v0.2 flattened migration behavior.
- existing primary-account CLI commands are unchanged.
